# 复核结束后，如何交付一份能复查的底稿

一份“已处理 1 条”的截图不能回答是谁处理、依据是什么、来源是哪一版，也不能让接收人重算完成率。`review-export` 把一个读取事务里的冻结清单、来源指纹、全部事件和派生状态一起交付；接收人无需原数据库或模型标签就能重放。

## 五分钟演示

先完成 [复核流程](REVIEW_WORKFLOW.md)中的认领和结案，然后在仓库根目录运行：

```powershell
$delivery = .\.venv\Scripts\creditvintage.exe review-export outputs/reviews.sqlite --out outputs/review-delivery | ConvertFrom-Json
$checkpoint = $delivery.bundle_sha256
.\.venv\Scripts\creditvintage.exe verify-reviews outputs/review-delivery --expected-sha256 $checkpoint
```

演示的结果为 48 条案例、2 条事件、47 条待处理和 1 条已结案，完成率为 1/48；`checkpoint_matched` 为 true。整个输出目录可复制到另一台安装了 CreditVintage 的机器，只需运行最后一条命令。Linux/macOS 使用已安装的 `creditvintage` 命令，保留同一参数。

目录包含 `source.json`、`review_queue.csv`、`events.json`、`status.json` 和 `manifest.json`。没有成熟预测、表现标签、模型训练数据或原分析目录；事件里的操作者、备注和材料引用仍需按实际数据权限处理。材料引用是文字，不包含附件原件。

导出不会覆盖已有目录。落盘失败会清理本次创建的文件，不留下一个可被当成完整交付的残包；进程被强制终止仍可能留有不完整目录，核验会拒绝缺失文件。重新导出时使用新的路径。

## 为什么哈希和重放都要有

| 检查 | 回答的问题 | 不能证明什么 |
| --- | --- | --- |
| 文件摘要 | 文件是否匹配包内清单 | 清单本身是否来自原作者 |
| 冻结清单规则 | 逐笔数据是否合法，优先级是否符合分数与 ID 的约定 | 名单是否确实来自声称的原分析 |
| 状态重放 | 每次操作是否合法，所有者、版本链和当前统计是否一致 | 备注内容或材料是否真实 |
| 外部检查点 | 当前包是否匹配另行保存的 manifest 摘要 | 检查点的保管者身份或可信度 |

故意把 `status.json` 的完成率改成 100%，同步更新文件摘要仍会失败，因为事件重放得不到这个数字。故意把一个合法结案理由改成另一个合法理由，并同时更新摘要，内部重放可以通过：它没有能力知道原话是什么。原先另存的 `bundle_sha256` 此时会拒绝新的包。

因此 `$checkpoint` 只是在演示中保存在当前终端。实际交付时，接收人需要通过独立且可信的渠道保存或收到它，不能从待核验包里重新计算一个摘要后把它当作外部证明。没有传入 `--expected-sha256` 时，命令仍核验内部一致性，但明确返回 `checkpoint_matched: false`。这不是电子签名、不可篡改存证或身份认证。

## 2026-11-10 源码修复：先核对清单，再重放操作

此前的清单重放检查了摘要、表头、唯一 ID 和连续序号，但没有重新检查每笔贷款的字段和排序。
一个可复现的反例是：把 `raw_pd` 改成字符串 `nan`，同步更新队列摘要、包内摘要和派生状态；
旧核验仍返回 `verified`。这不是合法的概率，也不能因为所有哈希一致而被接受。

包含本次修复的源码让数据库状态查询、复核提交、底稿导出和独立底稿核验共用以下规则：

- 申请 ID 满足原申请表的安全 ASCII 与长度约定；决策日使用严格的 `YYYY-MM-DD`，放款月份与该日一致。
- 本金是正整数分，落在 SQLite int64 的逐笔范围内；客群属于原申请表的两类枚举。
- 原始 PD 与校准 PD 都是 `[0, 1]` 内的有限数，边界 `0`、`1` 仍合法。
- 队列按校准 PD 降序、申请 ID 升序排列，并保留已有的连续 `review_rank` 约束。

即使重新计算了所有摘要，非法字段、错序或错误的并列顺序也会被拒绝。
检查在追加操作事件和创建交付目录之前完成，失败不追加事件，也不产生一份新底稿。
核验保持只读；已有合法 v1 清单和交付包的字段原文、文件集合与摘要格式不变。

这层规则仍不能发现所有合法的整体改写。例如把原始 PD 换成另一个合法值，并同步重写所有内部证据，
依然需要原先独立保存的检查点来辨别。因此它补充的是数据与顺序约束，不是来源认证。

**版本范围：** 本节对应包含本次修复的源码。已发布 `v0.8.2` 安装包保留早先的清单检查，
尚不包含这层修复；使用源码时按 README 的源码安装步骤操作。现有发布标签与安装包未被替换。
具体反例见 [清单契约测试](../tests/test_review_queue_contract.py)。

## 导出时有人继续操作怎么办

导出在一个 SQLite 读取事务中捕获源清单和事件，然后只用这些字节生成文件。导出后有人重开案例不会改写已交付包；新包和旧包可以包含不同事件数与结论。接收人核验的是这次交付所记录的状态，不是数据库现在的最新状态。事件序号界定这份包覆盖到哪里。

数据库和交付包复用同一份状态约束，避免导出程序采用另一套松散规则。测试通过伪造统计、非法版本、非所有者结案、非 UTC 时间、额外标签字段、原数据库删除和导出后重开来检查边界。

实现：[review_bundle.py](../src/creditvintage/review_bundle.py)；反例：[test_review_bundle.py](../tests/test_review_bundle.py)。
